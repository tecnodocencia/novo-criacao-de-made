## Item 3 — Mecânica de "troca" unificada entre os dois players (DECISÃO ARQUITETURAL)

**Diagnóstico confirmado:** `js/games/codigo-secreto/player.js` (autenticado) já
implementava corretamente a regra "engine original" antes desta sessão —
`replayGame()` reembaralhava o banco (via `renderPlayBank()`) e substituía
`rules.swap` posições do código secreto por cartas corretas diferentes, preservando
as demais. `js/play.js` (público/standalone) NÃO implementava troca parcial nenhuma:
`restartGame()` chamava `startGame()` → `createSecretCode()`, que sempre regenerava o
código inteiro do zero, ignorando `rules.swap` em todos os níveis. Essa regeneração
total — embaralhando entre si as mesmas 6 cartas corretas — é o que o usuário
percebeu como "troca de posição/localização" em vez de "troca de carta por carta
diferente", e só acontecia no link público, não no player autenticado. Confirma a
hipótese registrada em [[sessao_2026-08-19]]: bugs/divergências entre os dois
players são o padrão, não a exceção, nesse código.

**Decisão de arquitetura tomada:** extraída a lógica de troca parcial para uma
função pura e compartilhada, `applyReplaySwap(secretCode, correctCards, rules)`, em
`js/games/codigo-secreto/model.js` (já é o único módulo importado por AMBOS os
players — `player.js` via `./model.js`, `play.js` via `./games/codigo-secreto/model.js`
— então não exige nenhuma mudança de build/import novo). Algoritmo: sorteia
`min(rules.swap, codeSize)` índices do código secreto sem repetir índice, e para
cada um sorteia uma carta `isCorrect` que não esteja já presente em nenhuma posição
do código atual (por `content`, respeitando `rules.repeat`), substituindo só aquela
posição. Se o pool de cartas alternativas esgotar para um índice sorteado, essa
posição simplesmente não é trocada nessa rodada (comportamento herdado do código
original do `player.js`, não é bug).

**Onde isso foi plugado:**
- `player.js`: `replayGame()` agora chama `applyReplaySwap(...)` em vez de ter a
  lógica inline (comportamento idêntico ao de antes, só extraído).
- `play.js`: nova função `replayGame()` (module-scoped, não confundir com o método
  homônimo de `player.js` — são módulos diferentes) que decide entre
  `applyReplaySwap()` (se já existe `gs.secretCode` do tamanho certo) ou
  `createSecretCode()` (fallback, só quando não há código anterior compatível).
  `restartGame()` passou a chamar `replayGame()` em vez de `startGame()` direto.
  `startGame()` (usado só na primeira partida, vindo da tela de dificuldade) continua
  chamando `createSecretCode()` sempre — comportamento correto, pois não há código
  anterior para preservar.
- Extraído `resetGameScreen()` em `play.js` (render comum de tela pós-`secretCode`
  definido) para não duplicar as ~10 linhas de render entre `startGame()` e
  `replayGame()`.

**Por que isso importa para sessões futuras:** ao adicionar qualquer nova mecânica
de jogo que dependa do estado do código secreto entre partidas (streaks, dicas,
etc.), usar `model.js` como o lugar natural para lógica compartilhada entre os dois
players — é o único módulo que ambos já importam. Não duplicar lógica de jogo
inline nos dois arquivos de novo sem necessidade.

## Item 6 — Gerenciar Ranking no dashboard (novo recurso)

**Tabela:** `public_plays` (colunas: id, share_code, player_name, score,
attempts_used, won, difficulty_level, code_size, played_at) — ver
`supabase-migrations.sql` original. RLS já habilitado com policies de INSERT
("Anyone can insert...") e SELECT ("Anyone can read...") abertas para permitir o
player público sem login. **Não existia NENHUMA policy de DELETE.** Com RLS
habilitado e sem policy de DELETE, o Postgres nega delete para todo mundo por
padrão — inclusive o professor autenticado dono do jogo.

**Ação manual pendente do usuário:** criei `supabase-migrations-ranking-admin.sql`
(novo arquivo, raiz do projeto) com a policy que falta:
```sql
CREATE POLICY "Owner can delete public plays of their games"
    ON public_plays FOR DELETE
    USING (EXISTS (SELECT 1 FROM jogos WHERE jogos.share_code = public_plays.share_code AND jogos.user_id = auth.uid()));
```
Precisa ser rodado manualmente no SQL Editor do Supabase — sem isso, os botões de
remover/limpar ranking no dashboard não vão gerar erro (a policy de SELECT continua
funcionando), mas o DELETE silenciosamente afeta 0 linhas e o jogador continua
aparecendo depois de "removido". Documentado no próprio arquivo SQL. Essa policy
assume que `jogos` já tem uma policy de SELECT tipo `auth.uid() = user_id` para o
professor ver seus próprios jogos — nunca confirmada diretamente no painel do
Supabase (mesma ressalva já registrada em [[convencoes_decisoes]]), só inferida do
client (`listarJogos()` filtra por `user_id`).

**Implementação client-side:**
- `js/database.js`: 3 métodos novos em `dbService` — `listarRankingCompletoJogo(shareCode)`
  (como `listarRankingJogo` mas sem `.limit(20)`, usado pelo admin que precisa ver
  todo mundo, não só o Top 20), `removerPartidaRanking(playId)`, `limparRankingJogo(shareCode)`.
- `js/core/dashboard.js`: botão novo "Gerenciar Ranking" (âmbar, ícone `fa-trophy`)
  no card de cada jogo, ao lado do botão de compartilhar azul existente (mesmo
  padrão visual, `renderDashboard()`). Métodos novos: `manageRanking(gameId)` (abre
  modal, bloqueia com aviso se `game.share_code` ainda não existe — sem
  compartilhamento não há como ter ranking), `refreshRankingManageList()` (busca e
  re-renderiza a lista sem fechar o modal — usado após cada remoção),
  `removeRankingEntry(playId)`, `clearRanking()` (usa `this.showConfirm(...)`, o
  modal de confirmação genérico já existente em `js/core/modals.js`, mesmo padrão
  de `askRestart()`), `closeRankingModal()`.
- `js/core/state.js`: campo novo `rankingManageGameId` (rastreia qual jogo está
  aberto no modal, para poder re-buscar a lista após uma remoção sem precisar
  passar o id de novo).
- `index.html`: modal novo `#modal-ranking` (mesmo estilo visual do `#modal-share`
  já existente), inserido logo depois dele, antes do `<script type="module" src="js/app.js">`.
  `js/app.js`: adicionado fechamento por clique-fora (`window.onclick`) para o novo modal,
  seguindo o padrão dos outros modais.

**Decisão de escopo tomada:** a lista do modal mostra as MESMAS partidas que
aparecem no ranking público (`won = true`, ordenado por score desc/played_at asc),
sem o limite de 20 do ranking público (professor precisa poder gerenciar além do
Top 20). "Limpar Ranking Completo" apaga TODAS as linhas de `public_plays` para
aquele `share_code` — inclusive derrotas (`won = false`), que nunca aparecem em
nenhum ranking mas ficam na tabela; tratei como "reset completo das estatísticas
daquele jogo", não só "reset da lista visível". Se o usuário quiser separar esses
dois conceitos no futuro (limpar só vitórias vs. apagar tudo), replanejar.
